# R5/R6 candidate artifact and installation preparation

This is a review-candidate procedure, not authorization to merge, publish a replacement release, install on the owner host, or activate another phase. `TARGET_CONFIG=BLOCKED`. Refer to [Operating Guidance](../OPERATING_GUIDANCE.md), [topology contract](NGINX_VERIFIED_TOPOLOGY.md), [protected wrapper](NGINX_INSTALL_WRAPPER.md), and [Debian compatibility](DEBIAN_NJS_COMPATIBILITY.md).

## Provenance and distinct gates

The application baseline is the existing PR branch. Candidate builds check out the exact PR head, not the synthetic merge SHA. The complete existing validation runs before fresh images are built. Runtime Node 24.19.0 and Bun 1.4.3 base images use immutable Linux/amd64 manifest references, and dependency installation uses committed locks. FFmpeg and other distribution dependencies are not claimed bit-reproducible across repository updates; final Docker image identities and downloaded archive hashes identify the actual payload.

The candidate workflow has no registry-write permission or release-publication job. Its downloadable `review-candidate-*` archive is explicitly `REVIEW_CANDIDATE`; it cannot pass accepted-main publication authorization. Its verification job starts on another VM, rejects preloaded candidate image IDs, verifies archive/kit hashes, loads the delivered archive, and runs actual API/storefront images. No application source overlay, workspace bind mount, or dependency injection is accepted. QA credentials and certificates are generated for the disposable environment only. Production financial providers remain disabled.

The edge is built from authenticated, hash-pinned Debian packages compatible with observed Nginx `1.26.3-3+deb13u9`. This does not install anything on the owner host. The wrapper protocol fixture separately runs inside an owned privileged Debian Docker26 daemon container with its own socket and data volume. It does not mount the executor's Docker socket. Exact upstream Docker/Compose versions are distinguished from Debian package revisions and target binary identity.

`candidate-artifact-evidence-*` binds actual process-close exits, source SHA, both image IDs, archive hash, installation-kit hash and `PACKAGING.json` hash. It records real HTTPS/socket quotas, spoof/invalid proof/raw-byte/replay/concurrency checks, native/customer authentication and tenant isolation, same-origin navigation/screenshots/media, lifecycle failure/recovery and coordinated API/front namespace recreation. `exact-wrapper-evidence-*` is operator-protocol evidence, not application acceptance. The independent reviewer must assess both the implementation and the actual packaged evidence. Failed run artifacts remain evidence, never successful acceptance.

## Candidate execution and evidence retrieval

1. Push only the authorized PR branch. Open the **DIDAR CI** and **DIDAR candidate artifact gates** runs for that exact head.
2. Require all original gates: lint, types, four production builds, backend/native HTTP, all 32 browser cases, and fresh no-demo. Require candidate `build`, `verify`, and `wrapper-exact-debian` jobs to pass.
3. Download `review-candidate-<run>-<attempt>`, `candidate-build-evidence-*`, `candidate-artifact-evidence-*` and `exact-wrapper-evidence-*` using GitHub's Actions artifact links. Owner authentication to this repository may be required; executor-local image IDs are not download locations. Retention is 30 days, so transfer accepted evidence to owner storage before expiry.
4. In the extracted candidate root, run `sha256sum -c SHA256SUMS`. The original candidate manifest says verification pending; the separate verification artifact supplies its updated, source-bound manifest and checksum receipt. Keep both provenance records, and use the updated manifest only with its matching checksum set.
5. No source/docs commit may be substituted after image construction. A changed candidate must run these gates again. Record exact head, both image IDs, archive SHA-256, CI URLs and independent review in the PR. Stop for Chief Architect acceptance.

## Future accepted-main release (requires separate merge approval)

After approval and merge, fetch and resolve the resulting `origin/main` SHA. Do not re-label candidate images or assume the PR head equals the merge commit. Require successful exact-main push CI. Invoke **DIDAR authorized release** on `main` with `source_sha=<exact resulting main SHA>` and authorization `RELEASE <same SHA>` through the protected environment. The existing enable variable, reviewer approval, main-only dispatch and exact CI guards remain mandatory.

That workflow runs fresh validation/builds, exports fresh API/storefront images, creates the matching source-bound kit, and verifies downloaded images in a separate runner with the new topology gate. Publication remains closed if that gate fails. Registry references use manifest digests; Docker config IDs remain separate. The downloadable archive fallback includes SHA256SUMS, release manifest, INSTALL.md and the matching installation kit. Accepted-main publication must never consume `delivery_kind=REVIEW_CANDIDATE`.

## Existing-server preservation and target prerequisites

The observations supplied by runtime QA identify a legacy installation, not a verified rollback bundle: only an API source marker was observed; storefront marker and both OCI revision labels were missing. Preserve the existing images, exact configuration, PostgreSQL/Redis/media volumes, native identity state and secrets. Never substitute the old main release as that server's proven provenance.

Before target configuration is approved, runtime QA must supply actual socket peers at every hop, full Nginx build/module ABI and loaded configuration, exact Docker/Compose package provenance, project/network/volume/container IDs and namespace relationships, current image/source identities, listeners and TLS paths/SAN/chain/permissions. On-disk certificate verification is not independent Internet HTTPS acceptance. No trusted peer can be inferred from a bridge gateway, container address list or forwarding header.

Prepare encrypted/off-host PostgreSQL, Redis and media backups plus configuration and stable-secret custody. Restore them to separate disposable volumes and prove row/media checksums and identity/session preservation. Record migration compatibility and resource requirements before touching existing authoritative volumes. The wrapper requires backup/restore evidence, a fixed local Docker context, explicit existing resources and a matched image/config/signer bundle. It rejects unidentified legacy recovery and unsafe overrides. Separate namespaces require coordinated maintenance, stopping the consumer first, validated data-preserving migrations and recreating API before the shared-namespace storefront. There is no unsigned HTTP fallback.

The host module provisioning/secret plan is reviewed preparation only. Preserve other vhosts and services. Do not run provisioning, reload host Nginx, guess module paths, change TLS, or finalize allowlists on this task. Actual installation/update, target restart verification and independent public HTTPS acceptance belong to “03 — DIDAR Deployment & Runtime QA”, guiding the owner after approval.
