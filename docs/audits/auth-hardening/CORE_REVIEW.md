## Design review conditions sent before application edits

1. Direct API attribution must use the genuine socket peer, normalized consistently, rather than Express forwarded `req.ip`. Ignore untrusted `Forwarded`, `X-Forwarded-For`, `X-Real-IP`, and caller-chosen custom attribution headers.
2. A signature made by Next over an arbitrary incoming header only proves that Next saw the header; it does not establish the client's address. NextRequest lacks a default trustworthy socket peer. A forwarded-client assertion therefore needs an explicit, tested ingress contract that strips/overwrites the chosen header and excludes direct ingress, or a different explicitly limited identity design. No unknown target-host topology may be assumed verified.
3. A dedicated server-only assertion secret, authenticated allowed proxy peer, bounded timestamp and method/path/request binding prevent a direct client from forging/reusing a privileged assertion. No secret/client credential/raw password should enter logs, URLs, browser bundles or limiter rows. Invalid or missing required trust configuration must not downgrade into accepting unsigned identity.
4. Persistent abuse state must survive process restart, update atomically under concurrent requests, and bound state growth. IP rotation alone must not reset the relevant protection. A caller-controlled cookie/device ID alone is resettable and is not trustworthy network attribution.
5. A global victim-account failure counter must not become an unauthenticated account-lockout API. Conversely, checking every submitted password and only returning 429 after failure does not itself bound password guesses: the successful-password oracle still exists. Distinguish effective trusted-network budgets, account verification pacing/concurrency/challenge policy and observation-only counters; do not describe observation as prevention.
6. Keep canonical and native auth authorities separate. Do not patch the framework's global trust-proxy setting or native emailpass handlers merely to solve canonical DIDAR attribution. Verify original native user/member login, selected Seller, RBAC and tenant isolation alongside corrected customer/direct/proxy paths.
7. Actual affected evidence must cover old reproductions, unsigned/malformed/spoofed inputs, direct/proxy trust boundaries, multiple genuine client contexts, correct credentials after targeted/shared abuse, registration, concurrency, persistence/restart and PR #24 linked-target protection plus unrelated native compatibility. Capacity and real deployment ingress remain separately bounded claims.

## Coordinator design reviewed before application edits

The coordinator proposed a narrow Node HTTP first-hop authentication ingress adapter, preserving the existing Next customer app. The adapter obtains the actual socket peer, ignores caller forwarding assertions and signs a versioned HMAC over client network, timestamp, nonce, method, path and body digest. Next verifies that first-hop proof and re-signs the actual backend path. The backend accepts proof only with a dedicated sufficiently strong server-only key and configured exact proxy peers, validates binding/freshness and consumes the nonce once in PostgreSQL. Unsigned direct API requests use their socket peer; unsigned forwarding headers never become authority. Missing required proxy configuration/proof fails closed. Supported topology is explicit; arbitrary CDN/ingress placement is not inferred safe.

The final pre-implementation transport choice is **Policy A**: an entirely unsigned direct API request uses only its genuine socket peer, even when that peer happens to be on the assertion allowlist. The allowlist grants permission to present a verified assertion; it does not classify every request from that machine as a proxy request. Any present protocol assertion must be complete and valid or the request is rejected without fallback. Next independently requires its incoming first-hop proof/configuration before making an upstream authentication request; a missing Next proof must not consume an API auth bucket. An unsigned request from the Next machine has only that machine's network identity and is never treated as the original browser. A briefly considered strict peer-requires-proof alternative was superseded before implementation; the final tests must match Policy A.

Abuse policy proposed: persistent trusted-network spray budget (200/15 minutes) and trusted-network × normalized-account budget (20/15 minutes), plus bounded global/account work controls; no account-global deny/lock state. A capped account-global failure delay (at most 500ms) is pacing only, not a claim of complete distributed brute-force prevention. Asynchronous existing scrypt is bounded by four PostgreSQL-held global work leases and one per-network work lease. Lease expiry must not release capacity while work is still running. SEC-04 password trimming and native SEC-03 endpoints remain unchanged.

**Design review: APPROVED WITH IMPLEMENTATION CONDITIONS**, sent to the coordinator before app edits. A small real first-hop adapter is justified because NextRequest does not supply a trustworthy client socket. It is not a replacement storefront/native shell or an invented verified production topology. Review conditions are:

- Preserve the original first-hop nonce through Next re-signing and backend one-time consumption. Minting a new backend nonce on every replay of the front proof would invalidate the intended replay guarantee.
- Verify actual request bytes, not a JSON serialization of the parsed body. Next verifies raw incoming bytes before text decoding, then binds exactly the bytes sent upstream. Backend raw-body preservation must use the installed framework's supported route configuration.
- Validate timestamp bounds, method/path/nonce format, signature, peer allowlist and key configuration strictly. No unsigned downgrade, public secret or guessed proxy chain.
- First-hop upstream is fixed configuration; a request URL must not override its origin. Strip caller proof headers and avoid buffering unrelated media flows unnecessarily. Auth body limits and original non-auth behavior remain bounded.
- Use a dedicated held PostgreSQL connection for active work leases; release only after async password work actually finishes. Keep advisory namespaces separate from financial and identity locks. Concurrent failure/nonce/budget updates must be atomic and persistent.
- Keep the supported limit explicit: same real network/NAT can still share network throttles; genuine distributed networks and total resource exhaustion are not universally solved. A correct victim on another verified network must remain able to authenticate after attacker attempts against that account. Do not call a network quota a permanent account lock or claim zero possible denial of service.
- Provide an actual runnable first-hop adapter and precise public/private URLs, secret/configuration and local start instructions. Unconfigured direct API mode remains possible; an unconfigured Next login intentionally fails closed and must not be claimed as working legacy proxy transport. Do not advertise the private Next URL as the working authenticated public entry point without that qualification.

Current status: design approved; actual implementation and independent affected evidence pending. This reviewer owns this document only and has made no application edits or external test calls.

## Pre-freeze implementation findings

The shared server-only `@didar/auth-network` module was inspected directly: canonical IPv4/IPv6/mapped-peer normalization, strict one-header payload/signature alphabet, canonical base64url roundtrip, exact payload keys/version, constant-time HMAC, raw-body digest/method/path binding, 128-bit nonce and bounded clock window. The first-hop adapter is under `apps/storefront/auth-ingress.mjs`, within existing build-receipt source coverage. Native emailpass handlers and framework-global trust-proxy behavior were not patched.

Two concrete pre-freeze defects were reported to the implementer:

1. The first implementation inserted a permanent unique nonce row for every signed request, including quota-denied requests, but never pruned expired rows. The coordinator added indexed, bounded deletion of expired operational `didar_login_attempt` state (100 rows/request, `SKIP LOCKED`) and an additive `CREATE INDEX IF NOT EXISTS` expiry index. No user/session/business/financial row is pruned. Sixty-second nonce retention exceeds the protocol's maximum remaining proof-validity window (30 seconds old / 5 seconds future).
2. A regex-specific raw-body configuration is less specific than it appears in the installed framework. Pure local introspection of pinned `RoutesSorter`/`RoutesFinder` with the actual sort order returned `/didar/*` before the auth regex, selecting the catch-all config without `preserveRawBody`. That would make all correctly signed backend auth fail. The coordinator changed to exact string `/didar/login` and `/didar/register` configurations as requested; real signed-request proof is still required. The installed `defineMiddlewares` converts the typed `method` alias to `methods`, so that alias is valid. This is a framework integration finding, not a live/external test.

Current source review confirms nonce consumption is autocommitted independently of 401/429/session transaction rollback; the original ingress nonce/timestamp survives Next re-signing; unsigned direct requests use only socket peer; supplied invalid assertions cannot downgrade. PostgreSQL work locks use a separate two-key namespace and the exact leased connection is held until asynchronous crypto and the wrapped operation settle, then unlocked or destroyed. Native actor mapping, canonical identities, session persistence and PR #24 Product protections retain their original authorities. Final source/acceptance disposition remains pending the corrected frozen candidate.

Local developer/test orchestration now retains the advertised public customer port and starts the signing ingress in front of a private Next port, sharing an ephemeral process-only signing key and explicit local proxy peers. It does not rewrite owner environment files. The new ingress is source-covered by the existing build-receipt path rules. Counter persistence assumes a stable `COOKIE_SECRET`, which HMAC-namespaces bucket keys; changing that secret intentionally changes the keyspace. Same-network active-work rejection and shared NAT/network quotas remain explicit collateral limits, not a new per-account lock or a complete fairness/capacity guarantee.

Pre-build source disposition: **PASS for the approved bounded design, pending frozen-build independent acceptance.** The two concrete pre-freeze defects above are corrected in source. Ten new persistent HTTP/PostgreSQL cases exercise spoof/cookie rotation, normalized target budgets, distinct clients behind the same Next transport, targeted-account availability, direct/private proxy behavior, raw-byte/peer/nonce checks, replay through Next, concurrent quota, global work-slot rejection/release, bounded expiry cleanup and original native/customer sessions. Registration and actual API restart are additional independent-matrix requirements, not falsely covered by those ten test names. PR #24 regression sources must remain unchanged and run as affected preservation checks. No new final SEC-01/02 closure or production-readiness claim is made at this checkpoint.
